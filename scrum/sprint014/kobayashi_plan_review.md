# Sprint 014 Plan Review (Kobayashi)

Reviewed: `sprint_planning.md`, `sprint_backlog.md`, `handoffs.md` against `server/lib`, `server/test`, `scrum/scrumboard/lib` and `test`, `requirements/scrumboard.md` (SCB-01, 02, 05, 08, 09, 13, 17, 22), `requirements/common.md` (DEF-01), `docker/`, `scrum/usage.md` and PBI-086, 087, 094.

**Verdict: revise before the first developer starts.** 6 High, 10 Medium, 6 Low (22 findings). Every requirement ID the plan cites exists. The fixed names are mostly consistent, but several of them cannot be built or are unsafe as written (F1 to F6).

## High

**F1. Usage estimate contradicts `usage.md` and the Caution rule.** The plan anchors on 37% at 11:36 PM and predicts 60 to 65% at the end ("no notice"). The `sprint014` row already in `scrum/usage.md` records the Executive's newer reading, 48 / 44 at about 00:55, and its own estimate of about 73 / 47 at the end. That is at or above the 70% Caution level, so the Executive must be notified (the sprint then continues). Fix: replace the anchor with 48 / 44, state 48 + 25 = about 73 session and about 47 weekly, record the Caution notice, and drop "no notice, start now". Both files must give the same number. Also add the Kobayashi review and one round of fixes to the 25 (about 1 to 2 points), or say why it is covered.

**F2. The wave 2 integration test cannot be built as planned.** "The ScrumBoard server checked against the SuiteStream server (memory store) in the integration test" is Nakamura's `test/integration/*`. But `scrum/scrumboard/pubspec.yaml` states the package is independent of the root app with no path dependency and exact pins, and it has no `shelf`. `server/bin/server.dart` needs `DATABASE_URL` and OIDC and has no memory-store mode, and `pubspec.yaml` is in no ownership row. Fix, pick one and write it down: (a) Tanaka adds `server/tool/memory_server.dart` (a `MemoryStore` plus a fixed token, listening on a free port, printing it) and Nakamura's integration test starts it with `Process.start('dart', ['run', ...])` and skips with a recorded reason when `dart` is missing; or (b) both sides test the same JSON fixture file (one `contract/issues_api.json`, owner named) and no cross-package import is needed. Either way, name who owns any `pubspec.yaml` change.

**F3. `Store` has no way to read one issue, so the move check cannot run.** `issueMoveRefusal(from, to)` needs the current status, but `Store` gets only `listIssues`, `createIssue`, `setIssueStatus`. `listIssues` stops at 200, so an older issue is not found, and a read then write is a race. Fix: add `Future<IssueRecord?> getIssue(int number)` to `Store`, `MemoryStore` and `PostgresStore`, and make the write conditional (`UPDATE issues SET status=$2 WHERE number=$1 AND status=$3 RETURNING ...`, or one transaction); on zero rows return a refusal "changed meanwhile". Add a test for retired from every status and for the double-write.

**F4. Issue API security gaps.** The bearer design is sound (token only in the environment, constant-time compare, 503 when unset) but incomplete:
- The SuiteStream server is public (Authentik, `publicUrl`, `anyIPv4`). `--issues-url` may be plain `http://` to a remote host and would send the token in the clear. Fix: refuse `http://` unless the host is loopback or a name in the Docker network (state the rule in `issue_client.dart`; test it).
- Dart has no constant-time compare: say how (compare SHA-256 digests of both values with an XOR loop over equal-length bytes) and test a wrong token of equal and of different length.
- Minimum token length (for example 32 characters; `docker/.env.example` already uses `openssl rand -hex 32`): `ServerConfig.fromEnv` treats a shorter value as unset, with a test. The 401 answer is not specified: add `401 {"error":"unauthorized"}`, no `WWW-Authenticate` detail, and never log the header.
- The issue routes must be registered before `api.all('/api/<rest|.*>')` in `app.dart`, must not accept the session cookie as a substitute, and must skip the cookie path entirely (tests for both).
- The client must not follow redirects (`followRedirects = false`, so the token cannot move to another host) and needs a timeout, or one dead API hangs the board (SCB-13.g).
- Limits: a body limit for `POST /api/issues` (the existing `maxSettingsBytes` pattern) and field lengths (title, description, feature, requirement, assignee). Both are numbers, so they go in DEF-01 (F9).

**F5. The question number is not stable.** `PUT /api/questions/<n>/answer` uses the 1-based place in `scrum/questions.md`. By SCB-17.c and AGENTS.md agents delete answered pairs and add new ones at any time, so between the page's read and the Executive's click, place 3 can be a different question and the answer lands on it. Fix: send the number and the heading text (or a hash of the question) and have `answerQuestion` refuse with a reason when they differ; add the test "file changed after the page read it".

**F6. Accept effect has no order, failure rule or idempotence.** `applyLifecycle` returns lists and the server must then change requirement files (SCB-13.c order check), issues through the API (which can fail, SCB-13.g) and the sprint file, none of it atomic. Unspecified: which goes first; what happens when the issue API is down after the requirements were written; what happens for an item already `done` or `retired` (the order check refuses a "move" to the same or a lower status, so Accept could never finish); how stories under an epic under the sprint are found (the `Parent` chain); how `#N` members are told from requirement IDs. Fix: write the rule in the plan: apply the effects first (skip an item already `done` or `retired`, count it as success), write `accepted` last, so a failure leaves the sprint `complete` and Accept can be pressed again; return `ok:false` with the reason of the first failure. Name the walk (story to sprint through any epics). Test: issue API down, one item already done, one retired.

## Medium

**F7. `PUT /api/sprint` can bypass the lifecycle.** `saveSprint` sends whole blocks, now including `state` and `hold`, so a stale page (or any local caller) can set `accepted` or `running` without the SCB-08.f check and without the Accept effects; and a drag save from an old copy overwrites a state the lifecycle just wrote. Fix: `renderSprint` keeps the existing `state` and `hold` of a block id it already knows and ignores the body's values for it (only `applyLifecycle` changes them; a new block starts blank). Test both.

**F8. Blocks table with two new columns breaks the writer as described.** `_blockHeader` has 7 cells, `_parseBlock` requires exactly 7, `_replaceTable` keeps the header "as it was", and `_sameCells` compares cell counts. As written: a 9-cell row is skipped as unreadable, a file with a 7-cell header gets 9-cell rows, and every 7-cell row is rewritten when anything changes (SCB-02.f says unchanged rows stay as they were). Fix in Ito's task: read 7 or 9 cells; write the 9-cell header and separator only when a block gets a non-blank state or hold; write trailing blank `State` and `Hold` cells only for a block that has one; compare after trimming trailing empty cells. Also validate the new values (`state` in the five words, `hold` only `pause`, on `sprint` blocks only) and run `_checkCell` on them (SEC-S01).

**F9. Numbers outside DEF-01 and no owner for `requirements/common.md`.** `issuesLimit = 200`, the field lengths (F4) and the token minimum are numbers; `requirements/README.md` rule 1 and DEF-02 say numbers live in DEF-01 (`common.md`), and a growing list needs a stated limit. Decision 4 says "DEF-01 value is the one to cite when the Executive sets it" but no row exists. Takahashi's ownership names only `requirements/scrumboard.md`. Fix: add the DEF-01 rows (Issue list limit, Issue field lengths, Issue API token length) before wave 0, give `requirements/common.md` to Takahashi in the table, and make the constants cite the row.

**F10. Hidden dependency inside wave 1.** Tanaka's `lib/main.dart` imports `lib/src/features/questions_column.dart`, which Yamamoto writes in the same wave. Tanaka cannot compile or test until Yamamoto finishes. Fix: Yamamoto first publishes the class with its constructor (a stub that builds) in wave 0 or at the start of wave 1 and says so in `handoffs.md`; or move Tanaka's `main.dart` edit after Yamamoto in wave 2.

**F11. Badge design is contradictory.** The plan says the badge sits on the column heading, yet the heading is part of `QuestionsColumn` (Yamamoto's file), and the page's Questions slot is an empty `_Part` with no heading. It then says the page passes a `ValueNotifier<int>` "in via `QuestionsColumn.onOpenCount` in `main.dart`" but the `ScrumBoardPage` signature in the fixed names has no parameter for it, and `ScrumBoardApp` is rebuilt on theme or zoom change so the notifier must live in its `State`. Fix: draw the heading and the badge inside `QuestionsColumn` (it already gets the count) and drop the `ValueNotifier` and `onOpenCount` unless another widget needs the number; Tanaka's task then shrinks to the slot (`Widget? questions`). If the count is wanted outside, add the exact parameter to the page signature.

**F12. SCB-17.e is not met by decision 6.** SCB-17.e says a question is "marked new until the Product Owner has seen it". Decision 6 makes it a client-side flag per question number in memory: it says nothing about the Product Owner, it is lost on every reload (the page reloads when the stamp changes), and numbers shift (F5). Fix: either mark the plan "SCB-17.e partly met" and leave that row `backlog`, or put the "seen" mark in the file (a `Seen:` line the Product Owner writes, ignored by the board's answer write) and add it to the format in `scrum/questions.md` (needs an Executive decision: write it in `scrum/questions.md` and ask once). Do not list SCB-17.e as met.

**F13. Answer text can inject into `scrum/questions.md`.** The Executive's answer goes into a free-text field of a file that agents parse. Text with a line `## ...` or `Status: open` would add a question or change a status (the same hole SEC-S01 closes for the sprint file). Fix: `answerQuestion` rejects (or indents) any answer line that starts with `#` or `Status:` or `Question:` or `Choices:` or `Answer:`, enforces a length limit (DEF-01, F9), keeps line breaks, and replaces the file whole through a temporary file removed afterwards, serialized with `_serialized`, path through `resolveInside`. Tests for each.

**F14. `parseQuestions` shape is under-specified.** The file format is `## <asker, sprint> <short title>`, so asker and title are in one heading with no separator rule, yet the plan returns `asker` and `title` separately, and a multi-line `Question:` or `Answer:` is not mentioned. Fix: fix the split rule (for example the text up to the first `>` or `:` is asker; or return the whole heading as `title` and drop `asker`), say how continuation lines belong to the field above, how a pair with no `Status:` reads (open), and that unreadable pairs are skipped and written back untouched. Also say what "newest first" means (the file's last heading is newest).

**F15. The lifecycle button's mapping and "next to run" are not defined.** SCB-08.b: on a held sprint the button reads Start and pressing it lifts the pause; the plan's `start` is planned to running and `unpause` is a separate action, and `SprintLifecycleButton.onAction` gets one action string. Does Start on a held sprint call `unpause` only (the sprint then waits for a second Start, since AGENTS.md forbids a start without the word "start"), or `unpause` then `start`? Also `isNextToRun` is passed in, but who computes it and how (the first `planned` sprint block in table order after the last accepted one) is not stated, and the server's `pause` check ("not the next to run") needs the same rule. Fix: give one pure function `nextToRun(blocks)` (and the table state to action to label mapping) in `sprint_lifecycle.dart`, which is dart:io free so both the server and `lib/src/board` can import it; test the mapping for every state with and without hold; also test SCB-08's "Backlog block and stories have no button".

**F16. Missing arb keys.** The key list lacks keys the plan's features need: the "new" marker (F12), the answer text field hint (only `scbQuestionAnswer` is there and its use is unclear), the failure text when an answer cannot be saved, and the text when a lifecycle press is refused is covered but the answer one is not. Everything shown is a key (SCB-01.d). Add `scbNew`, `scbAnswerFailed` (placeholder `{reason}`) and the Answered key use, or state that the existing `scbMoveRefused` is reused. None of the 19 listed keys exists in `app_en.arb` today, so there is no clash; Yamamoto must also add the `@` description entries the other keys carry if the file does that.
